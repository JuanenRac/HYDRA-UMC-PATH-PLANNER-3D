HYDRA-UMC-PATH-PLANNER-3D - what's still not real, on purpose
================================================================

This file is the honest, complete list of what this planner deliberately
does NOT do yet, and why each item was deferred instead of half-built
alongside the real, tested single-agent RRT search that already exists
in src/rrt.rs. The README, CHANGELOG.md, docs/CLI_REFERENCE.md and the
module-level comments in src/main.rs, src/rrt.rs and src/obstacle.rs
each state their own short version of the relevant reason directly
inline, so none of them depend on this file to make sense on their own
- this is the one place the items are written up in full.

1. RRT* (path optimality via a rewiring pass) - DONE, off by default
   -----------------------------------------
   src/rrt.rs keeps the standard RRT as the default and adds RRT* behind
   `optimize_iterations` (> 0): cheapest parent among the neighbours,
   rewiring with the cost of the subtree following, and extra iterations
   after the first path. For one seed the result is never longer than the
   plain RRT. What is not there: a neighbour search faster than a scan of
   the tree (it is linear per iteration) and an asymptotic-optimality
   claim (the radius is a setting, not shrunk with the tree).

2. True multi-robot synchronized planning
   ---------------------------------------
   Today the planner plans one agent, one call, against a static
   obstacle set - it does not coordinate several robots' paths against
   each other in the same planning pass. This is real, scoped-out
   future work, not the "up to 32+ robots simultaneously" the README
   describes as the eventual goal. Building single-agent correctness,
   multi-robot coordination, and RRT* all at once would have meant
   debugging all three together instead of proving each independently.

3. Octree/BVH-accelerated collision checks at scale
   --------------------------------------------------
   src/obstacle.rs checks obstacles (spheres) with brute-force,
   per-obstacle math - the simplest 3D collision primitive that is
   still real and correct. That's fine at today's scale: a handful of
   arms and static safety zones sharing a cell, not thousands of
   colliders. An octree/BVH is real future work once a scene exists
   with enough obstacles for brute-force checking to actually matter.

4. A KD-tree that is rebuilt only by doubling
   -------------------------------------------
   Nearest-neighbour lookup uses src/kdtree.rs, a real incremental KD-tree.
   It is rebuilt balanced each time it doubles in size and both insert and
   search are iterative, so a monotonic insertion order (a long straight
   corridor) can neither overflow the stack nor degrade it to a list.
   What is not there: a library tree (e.g. kiddo) and a hard cap on nodes
   other than the iteration limit (semantics::MAX_ITERATIONS_LIMIT).

5. Exposing this as a network service (HTTP or hydra.common.v1 gRPC)
   -------------------------------------------------------------------
   This is a CLI over a JSON scenario file today, not a network
   service. Choosing HTTP vs. the ecosystem's shared gRPC contract
   (hydra.common.v1, see HYDRA-UMC-ORCHESTRATOR/proto/) is a real
   protocol decision that deserves its own pass once a real caller
   (HYDRA-UMC-JOB-DISPATCHER) is actually ready to integrate against
   this planner. The CLI is genuinely usable today
   (./run.sh scenarios/example.json) - it just isn't wired into the
   network yet.
